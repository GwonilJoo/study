## 0. 가장 먼저 읽을 것 — 사용자 프로필

**이 항목이 이 문서에서 가장 중요합니다.** 기술 정보보다 우선입니다.

### 사용자의 현재 수준

- **쿠버네티스는 처음입니다.** 클러스터, 파드, 디플로이먼트 개념을 오늘 처음 배웠습니다
- **도커는 사용 경험이 있습니다.** 컨테이너, 이미지, `docker ps` 같은 건 익숙합니다. 도커에 비유하면 잘 통합니다
- 클라우드(AWS 등) 실무 경험은 확인되지 않았습니다. VPC·서브넷·보안그룹을 이 대화에서 처음 설명받았습니다

### 반드시 지킬 것

사용자가 대화 중 **직접 요청한 사항**입니다.

> "난 처음 쿠버네티스를 공부하는 사람이야. 용어를 너무 쉽게 남발하지마. 용어에 대해서 잘 몰라."

이 요청이 나온 배경: 이전 답변들에서 CNI, 인그레스, 하드닝, Cluster API, kubespray 같은 용어를 설명 없이 던졌고, 사용자가 따라올 수 없었습니다.

**구체적 지침**

1. **새 용어는 처음 등장할 때 반드시 한 줄로 풀어 쓸 것.** 괄호에 영어 원어를 병기하는 정도로는 부족합니다
2. **지금 몰라도 되는 것은 아예 언급하지 말 것.** 선택지를 늘리면 혼란만 커집니다. 실제로 RKE2, Talos, Cluster API, kubespray를 꺼냈다가 되돌려야 했습니다
3. **도커에 비유할 수 있으면 비유할 것.** 사용자가 가진 유일한 발판입니다
4. **한 번에 하나씩.** 로드맵을 다 보여주지 말고 다음 한 걸음만 제시하세요
5. **"이건 아는 게 당연한가?" 싶은 질문도 환영한다고 명시적으로 알려줄 것.** 사용자가 물어봐야 진도가 정상적으로 납니다

### 잘 통했던 방식

- 실습 → 결과 관찰 → "왜 그렇게 됐는지" 설명 순서
- 표로 비교 정리
- 실패를 일부러 만들어보게 하기 (100Gi 요청해서 Pending 유도한 것이 특히 효과적이었습니다)
- 틀린 설명은 즉시 정정하기. 사용자가 날카롭게 되짚습니다 (아래 참고)

### 주의: 사용자가 검증합니다

사용자는 부정확한 설명을 그냥 넘기지 않습니다. 실제로 두 번 정정이 필요했습니다.

- "실무에서 kubeadm을 직접 쓰는 일이 줄고 있다" → "왜지? 사내 클라우드 구축하려면 필요할 것 같은데" → 부정확한 표현이었음을 인정하고 정정
- "가용 영역 간 통신 요금이 샌다" → "요금이 얼마나 드는데?" → 계산해보니 월 400원. 과장이었음을 인정하고 정정
- "이벤트가 1시간 만료돼서 없다" → "1시간이 안 지났는데?" → 단정한 것이 잘못이었음을 인정하고 다른 원인 제시

**추측을 사실처럼 말하지 마세요. 모르면 모른다고 하고, 숫자를 말할 거면 계산해서 말하세요.**

## 1. 현재 환경 상태

### 로컬 환경

| 항목                   | 값                                                 |
| ---------------------- | -------------------------------------------------- |
| OS                     | macOS (프롬프트: `gwonil@jugwon-il-ui-MacBookPro`) |
| 작업 디렉터리          | `~/k8s` (사용자가 `k8s`로 만들었음)                |
| Docker                 | 설치·실행 중                                       |
| kind                   | 설치 완료                                          |
| kubectl                | 설치 완료                                          |
| 쉘 프롬프트에 `(base)` | conda 환경 활성 상태                               |

### 클러스터

```
클러스터 이름: study
쿠버네티스 버전: v1.37.0

NAME                  STATUS   ROLES
study-control-plane   Ready    control-plane
study-worker          Ready    <none>
study-worker2         Ready    <none>
```

설정 파일: `~/k8s/kind-config.yaml`

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

### 재생성 방법

클러스터가 망가졌거나 없으면 이걸로 처음부터 다시 만들 수 있습니다.

```bash
cd ~/k8s
kind delete cluster --name study
kind create cluster --name study --config kind-config.yaml
kubectl get nodes
```

**망가뜨리는 걸 두려워하지 않도록 알려주세요.** 30초에 다시 만들 수 있다는 것이 로컬로 시작한 이유입니다.

### 남아 있을 수 있는 리소스

세션 종료 시점에 정리를 안내했으나 실행 확인은 못 했습니다. 먼저 확인하세요.

```bash
kubectl get deployments   # web, heavy 가 남아 있을 수 있음
ls ~/k8s                  # heavy.yaml 이 남아 있을 수 있음
```

정리:

```bash
kubectl delete deployment heavy
rm -f ~/k8s/heavy.yaml
```

`web` 디플로이먼트는 **다음 실습(서비스)에서 쓰므로 남겨두세요.** 없으면 이걸로 다시 만듭니다.

```bash
kubectl create deployment web --image=nginx --replicas=3
```

## 2. 다음에 할 일 — 서비스(Service)

**바로 이어서 진행할 주제입니다.** 사용자에게 이미 예고했고, 사용자가 "준비되면 말한다"고 한 상태입니다.

### 왜 서비스인가

기본 개념 5개(클러스터/노드/파드/디플로이먼트/서비스) 중 **유일하게 실습하지 않은 것**입니다. 개념 설명은 이미 했습니다.

현재는 `kubectl port-forward`로 접속하는데, 이건 임시 디버깅용이지 정식 방법이 아니라고 알려줬습니다. 서비스가 정식 방법입니다.

### 설명해야 할 핵심

1. **파드 IP는 계속 바뀐다.** 실습에서 파드를 지웠을 때 새 파드가 다른 IP로 뜬 것을 이미 봤습니다. 이 경험과 연결하세요
2. **서비스는 안 바뀌는 이름과 IP를 제공한다**
3. **라벨(label)로 연결된다.** `heavy.yaml`에서 `selector`와 `labels`를 이미 봤지만 설명하지 않았습니다. 여기서 설명해야 합니다
4. **부하 분산도 겸한다**

### 실습 시나리오 (제안)

```bash
# 1. 서비스 만들기
kubectl expose deployment web --port=80 --type=ClusterIP
kubectl get svc

# 2. 클러스터 안에서 접속해보기 (이름으로 접속되는 것 확인)
kubectl run test --image=busybox -it --rm --restart=Never -- wget -qO- http://web

# 3. 파드를 지워도 서비스 이름은 그대로인 것 확인
kubectl delete pod <파드하나>
kubectl run test --image=busybox -it --rm --restart=Never -- wget -qO- http://web

# 4. 서비스 타입 3종 설명
kubectl get svc
```

### 서비스 타입 — 여기서 kind의 한계를 만납니다

| 타입           | 용도                        | kind에서                      |
| -------------- | --------------------------- | ----------------------------- |
| `ClusterIP`    | 클러스터 내부 전용 (기본값) | 정상 동작                     |
| `NodePort`     | 노드의 포트로 외부 노출     | 동작하나 포트 설정 필요       |
| `LoadBalancer` | 클라우드 로드밸런서 연동    | **`<pending>`에 영원히 걸림** |

**`LoadBalancer`가 `<pending>`이 되는 것을 일부러 보여주는 게 좋습니다.** 이유를 이미 여러 번 설명했습니다: 클라우드의 `cloud-controller-manager`가 없어서. 이게 나중에 AWS로 넘어가야 하는 이유와 직결됩니다.

NodePort로 외부 접속을 하려면 kind 설정에 포트 매핑을 추가해야 하고, 클러스터를 재생성해야 합니다. 필요해지면 이렇게 합니다.

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 30080
  - role: worker
  - role: worker
```

## 3. 이후 로드맵

### 로컬(kind) 단계에서 남은 것

순서대로 진행하는 것을 권장합니다.

1. **서비스** ← 다음
2. **ConfigMap / Secret** — 설정값·비밀번호를 파드에 주입
3. **인그레스** — 외부 진입점. kind에서는 별도 설정 필요
4. **PVC** — 파드가 죽어도 남는 저장 공간
5. **Helm** — 패키지 설치 도구. 이후 도구 설치에 계속 쓰임
6. **metrics-server** — `kubectl top` 사용 가능해짐. 가벼움
7. **ArgoCD** — 깃 커밋으로 자동 배포 (GitOps)

**Probe(livenessProbe/readinessProbe)와 requests/limits를 의식적으로 다룰 것.** 실무에서 가장 자주 문제를 일으키는데 튜토리얼에서 대충 넘어가는 부분입니다. requests/limits는 이미 1일차에 다뤘습니다.

### AWS 단계 (2단계)

사용자가 "AWS에서 하겠다"고 결정했다가, 로컬 먼저 하기로 순서를 바꾼 상태입니다. **AWS는 로컬이 익숙해진 다음입니다.**

이미 합의된 구성:

| 항목      | 값                                        | 근거                                                                      |
| --------- | ----------------------------------------- | ------------------------------------------------------------------------- |
| 리전      | 서울 (`ap-northeast-2`)                   |                                                                           |
| 인스턴스  | **t3.medium** × 3 (2코어/4GB)             | t2.micro(1GB)는 쿠버네티스가 안 뜬다                                      |
| 구성      | 컨트롤 플레인 1 + 워커 2                  | 워커 2대여야 노드 장애 실습 가능                                          |
| OS        | Ubuntu 24.04 LTS                          | 자료가 가장 많음                                                          |
| 디스크    | 컨트롤 30GB / 워커 40GB, **gp3**          | 기본 8GB는 부족. gp3가 gp2보다 싸고 빠름                                  |
| VPC       | **기본 VPC 사용** (새로 만들지 않음)      | 학습 단계에서 변수를 줄임                                                 |
| 서브넷    | **3대 모두 같은 서브넷**                  | 실무에서는 AZ별로 나누지만, 지금은 문제 원인을 줄이기 위해 일부러 안 나눔 |
| 파드 CIDR | **192.168.0.0/16** (Calico 기본값)        | AWS 기본 VPC가 172.31.x.x라 겹치지 않음                                   |
| 설치 방식 | k3s로 먼저 완주 → 이후 kubeadm으로 재구성 | 설치 삽질에 며칠 쓰고 쿠버네티스를 못 만지는 상황 방지                    |

**보안 그룹 규칙** (가장 많이 막히는 지점)

| 유형        | 포트 | 소스                       |
| ----------- | ---- | -------------------------- |
| SSH         | 22   | 내 IP                      |
| 모든 트래픽 | 전체 | **이 보안 그룹 자신의 ID** |

두 번째 규칙이 핵심입니다. 소스에 IP가 아니라 보안 그룹 ID를 넣으면 "이 그룹을 붙인 서버들끼리 다 통한다"는 의미가 됩니다.

**AWS 진행 시 반드시 먼저 할 것**

1. **예산 알림 설정** (Billing → 예산 → 월 1만 원). 서버 만들기 **전에** 하세요
2. 키 페어 `.pem`은 재발급 불가 — 보관 강조
3. 실습 끝나면 인스턴스 중지. 완전히 끝나면 종료(Terminate)
4. 중지 후 재시작하면 **퍼블릭 IP가 바뀝니다** (프라이빗 IP는 유지)

**AWS 단계의 목표는 "서버 3대가 프라이빗 IP로 서로 ping이 되는 것"까지가 첫 관문입니다.** 여기서 안 되는 걸 모르고 쿠버네티스 설치로 넘어가면 원인을 못 찾습니다.

비용: 하루 8시간 × 한 달이면 약 5만 원 (인스턴스 3.2만 + 디스크 1.8만)

### 모니터링 (나중)

현재 사양(워커 4GB × 2)에서 프로메테우스(메모리 2~3GB)는 빡빡합니다. 대안으로 합의된 것:

- **Grafana Alloy + Grafana Cloud 무료 요금제** — Alloy는 노드당 100~150MB만 사용. 저장은 외부에서 처리하므로 서버를 늘릴 필요가 없음
- Alloy는 저장소가 아니라 **수집기**라는 점을 반드시 설명해야 합니다. 보낼 곳이 따로 필요합니다
- 그 전에 **metrics-server**(100MB 미만)를 붙여서 `kubectl top`부터 쓰게 하는 게 낫습니다

ArgoCD(1~1.5GB)는 프로메테우스보다 가볍고 학습 효과가 크므로 우선순위가 높습니다.

## 4. 참고: 대화에서 다뤘지만 지금 진도와 무관한 것들

사용자가 다시 물으면 답하되, **먼저 꺼내지 마세요.** 혼란만 늘립니다.

- **사내망/폐쇄망 구축** — Harbor(레지스트리), MetalLB(로드밸런서), Longhorn/NFS(스토리지), 사내 CA + cert-manager, RKE2, Talos. 사용자의 원래 관심사 중 하나이나 한참 나중 이야기
- **Bitnami 이슈** — 2025년 8월부터 공개 카탈로그 버전 태그 이미지가 `bitnamilegacy`로 이관되고 업데이트 중단. Helm 차트 설치 시 만날 수 있음. CloudNativePG, MariaDB Operator, Valkey 등으로 대체
- **Ingress NGINX 은퇴** — 2026년 3월 24일 프로젝트 종료. 신규 구축에는 Traefik, Envoy Gateway, HAProxy Ingress를 권장. 인그레스 단계에서 관련됨
- **GPU 클라우드 요금** — 최초 질문 주제. 하루 2시간이면 RTX 4090급 월 3~6만원, H100급 17~28만원 수준. 쿠버네티스에 GPU 노드풀을 붙이는 것은 상시 가동이 필요해 저사용률 시나리오와 충돌하므로 분리 운영 권장
