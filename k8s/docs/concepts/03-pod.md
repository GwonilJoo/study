# 파드 (Pod)

> 출발점: 도커 컨테이너와 뭐가 다른가 (2026-09-07)
> 대상: Kubernetes v1.37.0

## 한 줄 요약

쿠버네티스가 다루는 가장 작은 단위. 도커 컨테이너와 거의 같지만, **언제든 죽고 이름도 IP도 매번 바뀐다.** 이 성질이 서비스가 필요한 이유가 된다.

## 내용

### 도커 컨테이너와의 차이

지금 단계에서는 "파드 = 컨테이너 하나"로 봐도 된다. 다른 점은 수명 관리다.

| | 도커 | 쿠버네티스 파드 |
| --- | --- | --- |
| 죽으면 | 그대로 사라짐 | 관리자가 붙어 있으면 새로 만들어짐 |
| 이름 | 내가 정함 (`--name web`) | 자동 생성 (`web-5fc9f4bf66-l7vsv`) |
| IP | 재시작해도 대체로 유지 | **새로 만들어지면 바뀜** |

### 이름의 구조

```
web  -  5fc9f4bf66  -  l7vsv
 │         │             └─ 파드마다 다른 무작위 문자열
 │         └─ pod-template-hash. 레플리카셋 식별자 → 04-deployment-replicaset.md
 └─ 디플로이먼트 이름
```

### IP가 바뀌는 시점 — 정확히 언제인가

**"파드가 죽으면"이 아니라 "파드 객체가 새로 만들어지면"이다.** 이 구분이 중요하다.

| 상황 | 파드 IP |
| --- | --- |
| 파드 안의 컨테이너가 죽어서 재시작 (`RESTARTS` 숫자 증가) | **유지된다** |
| `kubectl delete pod` 후 컨트롤 루프가 새로 만듦 | **바뀐다** |
| 노드가 죽어서 다른 노드에 다시 뜸 | **바뀐다** |

> ⚠️ 확인 필요: 위 표의 첫 줄(컨테이너 재시작 시 IP 유지)은 아직 이 클러스터에서 실측하지 않았다. 파드의 네트워크 네임스페이스를 컨테이너가 아닌 파드 샌드박스가 쥐고 있기 때문으로 이해하고 있으나 미검증이다.

### 파드를 직접 만들지 않는 이유

파드를 직접 만들면 죽었을 때 아무도 되살리지 않는다. 그래서 실무에서는 거의 항상 디플로이먼트를 통해 만든다.

**예외가 하나 있다. 일회용 디버깅 파드.**

```bash
kubectl run test --image=busybox -it --rm --restart=Never -- wget -qO- http://web
```

| 옵션 | 뜻 |
| --- | --- |
| `--restart=Never` | 디플로이먼트를 만들지 말고 파드 한 개만. **이게 없으면 명령이 끝날 때마다 계속 되살아난다** |
| `--rm` | 끝나면 자동 삭제 (도커의 `docker run --rm`과 같음). `-it`와 함께 써야 한다 |
| `-it` | 컨테이너 화면에 붙기 |
| `-- <명령>` | `--` 뒤는 컨테이너 안에서 실행할 명령 |

`kubectl run`은 도커의 `docker run`에 해당한다. **앱 배포에는 절대 쓰지 않는다.**

### `-it`의 함정

명령이 아주 빨리 끝나는 컨테이너에 `-it`를 쓰면 출력이 유실될 수 있다.

```
warning: couldn't attach to pod/test, falling back to streaming logs:
container is in CONTAINER_EXITED state
```

붙기도 전에 컨테이너가 끝나서, kubectl이 로그 읽기로 전환하는 과정에 출력 일부가 사라진다. 실제로 30번 요청한 실험에서 6줄만 남았다.

**측정이 목적이면 `-it`를 쓰지 말고 로그를 나중에 읽는다.**

```bash
kubectl run loadtest --image=busybox --restart=Never -- sh -c '...'
kubectl logs loadtest
kubectl delete pod loadtest
```

`--rm`은 `-it`와 함께여야 하므로, 이 방식에서는 직접 지운다.

### busybox

크기 1.93MB짜리 리눅스 이미지(같은 노드의 nginx는 65.1MB). `sh`, `wget`, `ping`, `nslookup` 같은 기본 명령이 하나의 바이너리에 들어 있다. 앱이 아니라 **연장통**이다.

클러스터 내부에서만 통하는 주소를 확인하려면 클러스터 안에 있는 무언가가 요청을 보내야 하는데([07-cluster-dns.md](07-cluster-dns.md)), 그 심부름꾼으로 가장 가볍다.

## 왜 이렇게 설계됐나

**파드를 "고칠 수 있는 것"이 아니라 "버리고 새로 만드는 것"으로 정의했다.**

서버를 오래 살려두고 고쳐 쓰면 서버마다 상태가 달라진다. 어떤 서버는 패치가 됐고 어떤 서버는 안 됐고, 재현이 안 되는 문제가 쌓인다.

파드를 언제든 버릴 수 있게 만들면 그 문제가 사라진다. 대신 **파드에 붙어 있던 것(주소, 저장소)을 파드 바깥으로 빼야 한다.** 주소를 뺀 것이 서비스이고, 저장소를 뺀 것이 PVC다. 파드가 일회용이라는 전제에서 나머지 개념이 전부 파생된다.

## 이 설명이 깨지는 조건

- **"파드 = 컨테이너 하나"는 지금 단계의 단순화다.** 파드 하나에 컨테이너 여러 개가 들어갈 수 있다 (사이드카 패턴). 그 경우 컨테이너들은 IP와 저장소를 공유한다
- **파드가 항상 되살아나는 것은 아니다.** 되살리는 것은 디플로이먼트(레플리카셋)이지 파드 자신이 아니다. `kubectl run`으로 만든 파드는 지우면 끝이다
- **파드에 붙은 라벨을 바꾸면 관리자에게서 떨어져 나간다.** 되살아나지 않는 고아 파드가 된다 → [05-label-selector.md](05-label-selector.md)
