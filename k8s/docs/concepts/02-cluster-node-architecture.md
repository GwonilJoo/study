# 클러스터와 노드, 그리고 내부 구조

> 출발점: 여러 서비스를 운영하려면 어떤 구성이 좋은가 (2026-09-07)
> 대상: Kubernetes v1.37.0

## 한 줄 요약

클러스터는 서버 여러 대를 하나처럼 묶어 쓰는 것이다. **"3번 서버에 이거 올려줘"가 아니라 "이거 3개 돌려줘"라고 말하면 배치는 시스템이 정한다.**

## 내용

### 노드 두 종류

노드는 클러스터에 속한 컴퓨터 한 대다.

| 종류 | 역할 |
| --- | --- |
| 컨트롤 플레인 (control-plane) | 지휘. 어디에 놓을지 결정하고 상태를 기억한다 |
| 워커 (worker) | 실제로 컨테이너가 돌아가는 곳 |

### 컨트롤 플레인 구성요소

| 이름 | 역할 |
| --- | --- |
| kube-apiserver | 모든 것의 정문. **구성요소 간 직접 통신은 없고 전부 여기를 거친다** |
| etcd | 클러스터 전체 상태 저장소. 유일한 진실의 원천. 여기만 백업하면 복구된다 |
| kube-scheduler | 파드를 어느 노드에 놓을지 **결정만** 한다 |
| kube-controller-manager | 원하는 상태와 현재 상태를 비교해 차이를 메우는 컨트롤러 묶음 |
| cloud-controller-manager | 클라우드 연동 (LoadBalancer 생성 등). kind에는 없다 |

### 워커 구성요소

| 이름 | 역할 |
| --- | --- |
| kubelet | 노드의 에이전트. 파드를 실제로 띄우고 상태를 보고한다 |
| containerd | 컨테이너 런타임 |
| kube-proxy | 서비스 트래픽을 파드로 넘기는 규칙을 설치 → [06-service.md](06-service.md) |

### 배포 흐름

`kubectl apply` 실행 시:

1. kubectl → **API 서버** (인증·인가·검증)
2. API 서버가 **etcd**에 "원하는 상태" 기록 → **여기서 kubectl은 성공을 리턴**
3. **컨트롤러**가 감지 → ReplicaSet → Pod 생성 (아직 노드 미배정)
4. **스케줄러**가 노드 결정
5. 해당 노드의 **kubelet**이 컨테이너 실행

> **`kubectl apply` 성공은 "접수했다"는 뜻이지 "실제로 떴다"는 뜻이 아니다.**

### 컨트롤 루프

모든 컨트롤러는 같은 패턴을 무한 반복한다.

```
원하는 상태를 읽고 → 현재 상태를 관찰하고 → 차이를 좁힌다
```

파드를 강제로 지워도 다시 살아나는 이유. 누가 명령해서가 아니라 루프가 계속 돌기 때문이다.

이 패턴은 쿠버네티스 전체에서 반복된다. 디플로이먼트도, 엔드포인트슬라이스 명단 갱신도([06-service.md](06-service.md)), 전부 같은 루프다.

## 왜 이렇게 설계됐나

**"명령"이 아니라 "선언"으로 만든 것이 핵심이다.**

명령형이라면 "3번 노드에 컨테이너를 띄워라"를 누군가 실행하고 끝난다. 그 컨테이너가 나중에 죽으면 아무도 모른다. 복구하려면 그걸 감시하는 별도 장치가 또 필요하다.

선언형은 "3개가 떠 있는 상태를 원한다"를 저장해두고, 루프가 계속 그 상태를 향해 밀어붙인다. **복구가 별도 기능이 아니라 정상 동작의 일부가 된다.** 실패 처리를 따로 짤 필요가 없다.

그래서 모든 통신이 API 서버 한 곳을 지나게 만들었다. 상태가 etcd 한 곳에만 있어야 "원하는 상태"라는 개념이 성립하기 때문이다. 구성요소끼리 직접 통신하면 각자 다른 진실을 갖게 된다.

## 이 설명이 깨지는 조건

- **etcd를 잃으면 클러스터를 잃는다.** 노드가 아무리 많아도 etcd 백업이 없으면 복구할 수 없다
- **스케줄러는 배치를 "결정만" 한다.** 실행은 kubelet이다. 그래서 스케줄러가 죽어도 이미 뜬 파드는 멀쩡히 돈다. 새 파드만 `Pending`에 쌓인다
- **컨트롤 루프는 즉각적이지 않다.** 감지·판정에 시간이 걸린다. 노드 장애 시 실제 지연은 [09-troubleshooting.md](09-troubleshooting.md) 참고
